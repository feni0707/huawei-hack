## Главный факт, на котором строятся идеи

Генератор открытых тестов удаляет почти всегда одну из **последних труб той же длины**: ранг среди живых той же
длины — медиана 0–2 на 8, 11–15. Старые короткие во 2-й фазе 15 удаляет «ходок» вниз по стеку длины
(Δ ранга: 0 — 38 %, 1 — 17 %, 2 — 7 %). Отсюда два следствия: (1) дыра от удалённой трубы длины X, скорее всего,
сразу понадобится следующей X; (2) свежая труба длины X — главный кандидат на следующее удаление этой длины.

## Идеи по приоритету

### 1. «Бронь» свежей дыры под её длину (15, 14, 12, 13) — ожидаемо самое ценное
Когда удаляется труба длины X, её дыра на K укладок (K ≈ 30–60, или пока не придёт X) бронируется: её берёт
только X (точно) или труба, оставляющая остаток ≥ m и редкого размера. На хвосте 14 это ровно паттерн
«удалили X → кладут X»: сейчас X ± 1 занимают такую дыру с остатком 1, а следующая X идёт в хвост. Во 2-й фазе 15
так же уходят остатки 1–3 м между длинными (≈ 1.1 тыс. м = +0.25 % KPI). Это мягкая версия зон для длинных
(жёсткие зоны для длинных давали 0.88 — резерв под колебания численности 33 длин).
Сигнал «бронировать или нет» — та же доля удалений «по стеку длины» (lifoHit), что гейтит зоны.
Проверка: two_phase_real, gen_robust3 (fifo/sawtooth/del_half_group — там брони быть не должно), open 14/12/13.

### 2. Модель будущего «по стеку длины» для rollout-поиска (12/13/14, класс 15)
Rollout с bootstrap прошлой истории был хуже best fit (−0.7…−1.1 %), а оракул давал +0.9 %: мешало незнание,
КТО умрёт. Теперь есть хорошая модель: удаление = выбрать длину (по частоте недавних удалений длин), ранг внутри
длины ~ Geom(0.5). Rollout H = 50–100 только при спорных решениях (разница цен кандидатов < порога), 8–16
сэмплов, best fit внутри. CPU сейчас 0.53 с — запас ×5. Начать с офлайн-проверки на 13/14/12 (`scratchpad roll2.cpp`
из прошлого эксперимента), потом на lifo/alternating.

### 3. Генератор для класса 12/13/14 с удалениями по стеку длины
Старые `alternating`/`lifo_mix` удаляют по глобальному рангу; на них решения 12/13/14-типа проверяются плохо
(так же, как старый `two_phase` не видел выигрыша зон). Сделать `scripted_lifo`: сценарные фазы (серии
«L 1 L−1 1…», циклы 5/10/5/10, «удалили X → положили X», рост без удалений), удаление — выбор длины + ранг внутри
длины Geom; калибровать по статистике рангов и по оракульным границам, как two_phase_real.
Это предусловие для честной проверки идей 1–2 и для CMA-ES.

### 5. Раскладка коротких сверх «порядка PID» (15)
Граница по коротким при зонах 12.9 тыс. м, идеальная «по длинам в порядке PID» — 12.6. Основные потери — длины
1–3 (нужно ≥ 8/L умерших подряд). Варианты: (а) не открывать отдельные зоны для 1–3, а класть их «стопками»
внутри зон длинных коротких так, чтобы ходок одной длины освобождал кусок ≥ 8; (б) участки 1–3 крупнее (ходок
режется границами участков). Сначала посчитать оракульные границы вариантов (`scratchpad seg.py`), потом делать.

### 6. Хвостовые эффекты в конце теста
На 15 ≈ 1.2 тыс. м — дыры от удалений за последнюю тысячу команд; на 14 все потери — в конце. Конец теста
неизвестен, но n ≤ 200 000: в последние ~2 000 команд до 200 000 (если тест туда дошёл) предпочитать точные
попадания в старые дыры хвосту. Прошлый «эндшпиль» (чистый best fit) был хуже — пробовать только как надбавку к
линейной оценке, и только с бронью из идеи 1.

### 8. Асимметричная вложенность по классу жизни (по мотивам LLAMA, ASPLOS 2020) — ОТКЛОНЕНО (H11, `build/hyp/11/REPORT.md`: DEV −0.18…−0.37 % у всех 6 вариантов)
Источник: Maas et al., «Learning-based Memory Allocation for C++ Server Workloads» (кода в открытом доступе нет,
алгоритм — из §3 статьи). Куча делится по классам времени жизни; дыры в долгоживущем участке переиспользуются
**только объектами строго более короткого класса** (умрут раньше «резидентов» — дыра снова откроется, а не
зацементируется); когда резиденты умерли, участок переклассифицируется вниз; пережил дедлайн — класс вверх.
Перенос на нашу задачу: класс трубы ≈ глубина в стеке своей длины (свежая на вершине активно удаляемой длины —
короткоживущая; столкнули вниз новые той же длины — «повысилась»; переклассификация по событиям, не по таймеру).
Правило: в дыру, у которой оба соседа — «долгожители» (глубина ≥ d или возраст ≥ a), класть только трубу,
которая станет вершиной стека активно удаляемой длины; иначе — как сейчас. **Жёсткий фильтр кандидатов, а не
штраф в линейной оценке** — этим отличается от отклонённых H05 (симметричный штраф за разницу смертей соседей),
H03 (возраст дыры) и «риска соседа среди 1–2 последних своей длины» (EXPERIMENTS.md). Гейт — lifoHit, как у зон.
Ожидание скромное (десятые доли % на 12/13/14, two_phase_real): резерв 15 — в информации 1-й фазы, правило её не
добавляет. Проверка — по `build/hyp/PROTOCOL.md`.

### 9. Время жизни по заменённой трубе (по мотивам SepBIT, FAST'22) — низкий приоритет
SepBIT (лог-структурированное хранилище Alibaba) предсказывает жизнь новой записи по прожитому той, которую она
заменила: бинарный класс «короче / длиннее средней продолжительности ℓ», ℓ пересчитывается по факту. У нас
аналог — «удалили X → кладут X»: новая X наследует класс прожитого удалённой X (не среднее по длине, как в
отклонённой H05). Использовать только как признак выбора стороны остатка / потока, НЕ как фильтр или штраф
(H05/H11 показали, что штрафы поверх gapCost не окупаются). Цель — kv_update/steady, 14. Ожидание ≈ 0…0.1 %.
Источник: Wang et al., «Separating Data via Block Invalidation Time Inference…», arXiv 2104.12425.

### 10. Оффлайн-оптимум маленьких тестов через MiniMalloc (инструмент, не посылка)
`google/minimalloc` (ASPLOS 2023, код открыт) точно решает оффлайн DSA (интервалы жизни известны): поиск
с отсечениями по «каноническим» решениям. Вход — CSV (id, начало, конец, размер) + ёмкость; бинпоиск по ёмкости
даёт OPT. Зачем: честная оффлайн-граница вместо LOAD из `kpi_upper_bound.py` — на `robson` оракул-BF 0.72 при
LOAD-границе 0.94, неясно, сколько из разрыва достижимо даже оффлайн. Нюанс: у нас цель — длина траншеи
в КОНЦЕ (= пик, кратный 20), а не высота упаковки в пике; для KPI это одно и то же с точностью до округления.
Применимо к тестам ≲ 10⁴ труб (дальше перебор не сходится). Теория: при max размере ≪ LOAD оффлайн OPT ≈ LOAD
(Buchsbaum et al. 2003) — проверить, так ли это на 5/9/10 и robson.

### Из литературы — уже покрыто или неприменимо (не повторять)
- First fit на полуоси сам сортирует размеры (мелкие влево) и асимптотически оптимален при пуассоновской
  нагрузке (Ernst–Stolyar–Wang, arXiv 2404.03797) → на «случайных» тестах резерва нет; зоны по длинам — то же
  самое, но явно. Подтверждено: на `robson` FF ≈ BF.
- Death-time discrimination / когорты (Wilson 1995) — потоки (приняты), H2 (отклонена). Age-match (Beck 1982) —
  H05, ломается при «тяжёлом хвосте» жизни (наш LIFO по длине). Half fit — признак «доля длины остатка».
  Wilderness preservation — хвост последним. Гибрид BF/AOFF Шора — не проверен, ожидание ≈ 0 (H04 next-fit вреден).
- LLAMA — выигрыш от возврата пустых страниц ОС, у нас траншея не укорачивается (H11 отклонена).
- Bender et al. 2026: Ω(log M) для любого онлайн-аллокатора; при дроблении запросов — log log M (у нас трубу
  резать нельзя). Ловушка по их нижней оценке — семейство `robson` в `gen_general.py` (scorefit −0.26 % к BF).
- Готовых решений этой задачи (GitHub, Codeforces/Huawei Challenge 2022–2026) не найдено (поиск 2026-10-21).
