# Материалы хакатона (`materials/`)

Архив с NSUts (изначально скачан как папка `2`). Содержимое не меняем — это эталон проверяющей системы.

| Файл | Что это |
|---|---|
| `tests/1.in … 15.in` | 15 открытых тестов (закрытые 16–30 недоступны). |
| `interactor.cpp` | Исходник интерактора — **главный источник истины** о правилах проверки (см. ниже). |
| `testlib.h` | testlib 0.9.34-SNAPSHOT (Mike Mirzayanov), библиотека для интерактора. |
| `interactor` | Готовый интерактор, Linux x86-64 ELF (static). **На macOS не запускается.** |
| `interactor.exe` | Готовый интерактор, Windows x64. |
| `runner.py` | Официальный скрипт локального прогона. |

## Формат файла теста `*.in`

```
<weight> <n>
<cmd_1>
...
<cmd_n>
0
```

- `weight` — вес теста (0.1 / 1 / 4 / 10), совпадает с таблицей из условия.
- `n` — число команд, **не считая** финального `0`. Интерактор читает ровно `n` команд, завершающий `0` в файле игнорирует
  и сам посылает решению `0` после последней команды.
- `cmd > 0` — уложить трубу длины `cmd` (1..40), `cmd < 0` — удалить трубу с PID `-cmd`.
- Все удаления в открытых тестах корректны (удаляется существующая, ещё не удалённая труба).

## Точная логика интерактора (`interactor.cpp`)

Траншея моделируется массивом клеток по 1 м (`cells[i] = PID` или `-1`). Для каждой команды по порядку:

1. Печатает команду решению (`cout << instr << endl`) и **ждёт ответа** — это честный online, следующей команды не видно.
2. **Укладка** (`instr > 0`, PID = порядковый номер укладки, с 1):
   - читает `cnt` и `shift`, каждый — целое в `[0, 100 000 000]`, иначе ошибка формата;
   - `cnt` раз: проверяет `cells.size() < 100 000 000`, затем добавляет 20 клеток в конец;
   - проверяет `shift + len ≤ cells.size()` («end of new pipe … is out of trench»);
   - проверяет, что все клетки `[shift, shift+len)` свободны («new pipe X collides with pipe Y»);
   - занимает их.
3. **Удаление** (`instr < 0`, `id = -instr`):
   - читает `shift` в `[0, 100 000 000]`;
   - требует `shift == позиция трубы id` («position of pipe … is wrong»), освобождает клетки.
4. После всех команд печатает `0`, считает `occupied = #занятых клеток`, `total = cells.size()`.
   `KPI = occupied / total`, в `score.txt` пишет `KPI * weight`, в stderr —
   `Score = occupied/total * weight = KPI x weight = score`.

Следствия:
- Ответ решения на укладку — два целых через пробел, на удаление — одно целое; разделители — любые пробельные символы
  (testlib читает токены), но **после каждого ответа нужен flush**, иначе deadlock/Timeout.
- Любая ошибка → Wrong Answer → KPI = 0 на этом тесте.
- Длина траншеи на выходе ≤ 100 000 000 м. Траншея никогда не укорачивается.
- Решение может само хранить позицию каждой трубы — интерактор просто сверяет её при удалении.

## Как запускать локально

Удобные обёртки (работают на macOS и Linux, собирают интерактор из исходников в `build/interactor`):

```bash
scripts/run_tests.sh build/my_solution
```

```bash
scripts/run_tests.sh build/my_solution materials/tests/15.in
```

```bash
scripts/debug_run.sh build/my_solution materials/tests/8.in
```

- `run_tests.sh` — через официальный `runner.py`; печатает время, память и **взвешенный** score по каждому тесту + `Total`
  (максимум на открытых тестах — 32.1).
- `debug_run.sh` — один тест без runner'а, показывает stderr интерактора: точную причину WA или `Score = a/b ...`.
  Транскрипт ответов решения — `build/debug/tout.txt`.
- `scripts/analyze_tests.py materials/tests` — статистика по тестам; `scripts/kpi_upper_bound.py materials/tests` — верхние оценки KPI.

### Подводные камни официального `runner.py`

- stderr интерактора уходит в `DEVNULL` — причины WA не видно. Для отладки — `scripts/debug_run.sh`.
- Решение запускается `Popen(solution)` без `shell=True`: на macOS/Linux строка `"python3 sol.py"` не работает
  (пытается запустить файл с таким именем). Решение должно быть одним исполняемым файлом (для Python — скрипт с shebang и `chmod +x`).
- Если нет `psutil`, runner сам ставит его через pip.
- Пишет `score.txt`, `answer.txt`, `report.txt` в текущую директорию (обёртка делает `cd build/run`).
- При `-d` порядок тестов — порядок `os.listdir` (обёртка сортирует).
- Время, которое показывает runner — user CPU решения, измеряемое опросом раз в 10 мс (грубо).

### Вручную (как в условии)

На Linux из `materials/`: `python3 runner.py -d tests ./my_solution`.
На Windows: `python runner.py -d tests my_solution.exe` (по умолчанию берётся `interactor.exe`).
