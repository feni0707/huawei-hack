# Анализ потолка онлайн-решения (Claude, 2026-10-20): что проверено сверх scorefit

Ветка `claude/ensemble` (от `feni/scorefit` @ f04b1c1). **Решение для посылки не менялось: лучшее честное — `solutions/scorefit.cpp`
(open 30.154 на MSVC/Windows, WA/TL = 0, CPU ≤ 2.2 с на 15 с учётом ввода-вывода Windows).** Всё ниже — эксперименты, которые
не дали прироста, и инструменты, которыми их можно повторить. Эксперименты лежат в `scripts/exp/`, в `solutions/` ничего не добавлено.

## Главный вывод

Потери `scorefit` относительно верхней оценки (UB) — это не неточность правил, а **нехватка информации о будущем**. Доказательства:

| Эксперимент (оракул = знает будущее) | Результат |
|---|---|
| Оракул смерти только коротких 1-й фазы (feni) | 15: 0.961 → 0.974 — недостижимо, смерть среди «окна» случайна (P(жертва) ≈ 0.5, соседи почти независимы) |
| Rollout по настоящему будущему, H = 30…1000 команд, до 4 кандидатов (`scripts/exp/lab_roll.cpp`, ROLLMODE=1) | 12: 10340 → 10300, 13: 3280 → 3260 (−1 докопка), 8: 4700 → 4680; до UB (10260/3220/4640) далеко |
| Оракул срока жизни: штрафы «мёртвого остатка» выключены для коротко живущих труб | ±0.1…0.4 % (шум) |
| Оракул срока жизни: сосед по границе дыры должен умирать вместе с новой трубой (`K14` в `solutions/ensemble.cpp`) | 8/12/13/14/15 не лучше (13: 0.973 → 0.944…0.961), только тест 10 → UB |
| Оракул «долгожитель не ломает дыру» (`K12`) | 8 +0.4 %, 13 −1.2 % при H = 20, остальное 0 |
| Оракул конца теста (последние K команд — без выжидания точного попадания) | 15 +0.1 %, 12 −0.2 %, 11 ±0.1 % |
| Настройка весов линейной оценки прямо на самом тесте (in-sample!, sep-CMA-ES, 40 поколений) | 13 +0.6 %, 12 +0.2 %, 8 0, 10 → UB. Test-time tuning по префиксу не окупится |
| Оракул-лучший из 6 конфигураций scorefit по тесту | +0.09 из 35.4 (≈ +0.25 %); честный выбор по теням дал бы около половины |

UB достигается только глобальной офлайн-раскладкой (первое подходящее место во времени-пространстве в порядке убывания смерти):
`claude/portfolio` — `scripts/offcore.h`. Онлайн ей эквивалентно только знание всей будущей последовательности, т.е. распознавание теста.
Это запрещено правилами команды и просьбой автора, поэтому не делалось.

## Отрицательные результаты (чтобы не повторять)

1. **Парные зоны для 1-й фазы 11/15** (пары (X, 8−X) по 8 клеток вместо зон одной длины): 15: 0.9612 → 0.9511. Моделирование «победы» на i.i.d.-жертвах
   (`scripts/arrsim.py`: мёртвых клеток 32.7 % → 24.1 %) НЕ подтверждается на реальных наборах жертв (`scripts/shortproxy.py`, `arrproxy.py`:
   зоны 12.6 тыс. клеток, пары 12.8, по времени 13.1, блоки со сортировкой 12.7–13.9, PID-порядок 14.6). Причина: жертвы разных длин
   независимы (P(жертва | сосед по PID — жертва) = 0.43), а внутри длины идут цепочками; парные дыры ровно 8 — «монокультура»: 8-труб
   на них не хватает (в конце 338 нетронутых дыр по 8).
2. Размер зоны ZSLOTS, ZMINALIVE, ZSHARE: плато (±0.05 %).
3. Зоны для `alternating` (3 частые длины): −0.2…−2 %.
4. «Мёртвый остаток → в хвост» с порогом 1…4 (в том числе с докопкой): alternating −0.1…−2.5 %.
5. Сегрегация по рангу в стеке длины как признак опасности соседа: вероятность смерти за 10 команд ≤ 13 % даже для ранга 0…3 (`scripts/rankhaz.py`).
6. Ансамбль `линейная оценка / чистый best fit` (веса LW = (1, 0, …)): на 120 случайных сценариях (`scripts/gen_scen.py`) оракул-выбор даёт
   +0.06 %; только на моём классе `bimodal` (мелкие 1–3 живут долго, крупные 30–40 — недолго) линейная оценка на 4–5 % хуже best fit (виновны веса LW5/LW6,
   «остаток равен ходовой длине»). Наборы: `scripts/gen_tests2.py`, `scripts/gen_robust3.py`.
7. **Lookahead на 2–4 команды по прогнозу команд** (n-gram по токенам: «длина укладки», «длина+ранг», «дельта PID к прошлой жертве», «расстояние назад»,
   выбор представления по недавней точности, допуск по точности прогноза на первых 2 шагах; `scripts/exp/lab_roll.cpp` + `patch_roll_*.py`):
   в ЛАБОРАТОРНОЙ версии тест 10 → 0.797–0.800 (потолок), но лаборатория отстаёт от чистого scorefit (LW17 = 8.7 вместо 50). Относительно весов чистой версии прирост
   +0.4 % на тестах семейства 10 и +0.1 % в среднем по 35 вариантам открытых тестов, при единичных потерях −0.2…−0.4 %. Для 200k-траншеи клонирование состояния
   не масштабируется — нужна отдельная журналируемая структура. Не стоит.

## Положительные находки (не изменяющие посылку)

* `scorefit` валиден на всех моих наборах (мутации открытых тестов `build/mut`, fuzz, 120 сценариев, 200k-тесты шести классов): WA = 0 (кроме `single_del`, где KPI = 0 по определению).
* Потери `alternating` при 200k — не транзиентные скачки, а медленное накопление мёртвых остатков 1–2 м (≈ 4 клетки на 1000 команд) (`scripts/exp`: `simc` + `FRONT=`).
* Тест 11 (малая двухфазная): ~3.5 % траншеи — «ждущие» дыры 8–19 м от последних удалений (конец теста), ещё ~4 % — мёртвые остатки коротких.

## Что имеет смысл дальше

1. Если нужен ещё +0.1…0.2 балла на закрытых тестах — только повышение выборки при настройке (больше классов, в т.ч. `scripted_lifo` из `docs/IDEAS.md` №3).
   Любая единичная эвристика даёт ±0.1 % (шум стенда).
2. Журналируемый (undo) аллокатор + lookahead по прогнозу команд даст до +1…2 % только на скриптовых тестах семейства 10 (вес 1 среди открытых).
3. Выбор конфигурации теням (портфель) ограничен сверху +0.25 %; цена — ×2…3 CPU.
