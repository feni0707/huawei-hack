# Вариант «universal»: независимый движок best fit + арены по классам смерти

- **Владелец:** агент (ветка `agent/universal` от `feni/scorefit`). **Файл:** `solutions/universal.cpp` (standalone, C++17).
- **Стенд:** `scripts/sim2.cpp` + `scripts/simrun.py` (in-process, проверка как в `interactor.cpp`), `scripts/winbench.py`
  (Windows-порт `bench.py`: настоящий интерактор, CPU через `GetProcessTimes`).
- **Статус на момент написания:** open **29.3007 / 32.1** (scorefit 30.1539, naive 4.9129), WA/TL = 0;
  на 20 классах `build/robust` средний KPI **0.8383** (scorefit 0.8473). Ниже — где выигрываем и где проигрываем.
- **Ресурсы (настоящий интерактор, Windows):** пик памяти 20.5 МБ на `build/gen/stress/1.in` (200 000 труб по 40 м),
  11.2 МБ на 15. CPU в одинаковых условиях (-j 8, open): universal 4.73 с на 15 (Σ 6.70), naive 4.31 (Σ 6.41),
  scorefit 4.19 (Σ 6.33) — на Windows почти всё это flush ответа в пайп; алгоритм в стенде стоит 0.01–0.05 с на тест
  (на Linux у naive на 15 документировано 0.39 с, значит и у нас ожидается ≈0.5 с при лимите 5 с).

## Грабли, которые стоят отдельного абзаца

**`fread(stdin, 1, 65536, ...)` на пайпе блокируется до заполнения буфера.** Стенд `sim2.cpp` подаёт команды
из памяти, поэтому ошибку не видит: решение отвечает мгновенно и показывает 29.28. Настоящий интерактор
присылает по одной команде и ждёт ответа → решение ждёт 64 КБ → **TL на всех тестах, где ответов много**
(в первой версии: 402 прогона, десятки TL, open = 0). Лечится `read()`/`_read()` вместо `fread`.
Проверять решение ВСЕГДА через настоящий интерактор (`scripts/winbench.py`), даже если стенд зелёный.

## Главный факт, из которого всё следует

KPI = (занятые клетки в конце) / (длина траншеи в конце). Множество живых труб в конце задано входом,
траншея не укорачивается ⇒ **единственная управляемая величина — число докопок по 20 м**. Значит метрика
качества стратегии = `(T_final − 20·ceil(peak_live/20)) / 20` лишних блоков. Задача — online dynamic storage
allocation с монотонным ростом кучи; «красивая» укладка важна только тем, сколько докопок она экономит.

## Механизмы

1. **GapSet** — свободные промежутки: `set<(len,start)>` для best fit + `map start→len` и `map end→start`
   для слияния за O(1) при удалении; ленивое удаление устаревших записей. Промежутки арен помечены
   владельцем (уникальный тег блока) и не видны best fit.
2. **Best fit + сторона остатка по «молодости» соседа.** Удаляется обычно более молодая труба (находка команды),
   поэтому остаток прижимается к более молодому соседу: когда тот умрёт, остаток сольётся с его клетками.
3. **Арены по классам смерти (новое).** Если подряд кладут одну и ту же длину L (серия без удалений ≥ 8),
   труба ранга r идёт в поток `r mod 2`, каждый поток растёт в своих блоках ограниченной ёмкости.
   В классе «серия одинаковых труб, затем удаляют каждую вторую» жертвы оказываются в одном потоке, и их
   смерть освобождает непрерывный кусок, пригодный для длинных труб. Неиспользованный остаток блока
   при конце серии возвращается в общий фонд.
4. **Гейт арен по направлению длин (новое, оказалось решающим).** Арены помогают только там, где
   освободившиеся дыры НЕ годятся для будущих труб (группы длин растут: тесты 5/9), и вредят там, где годятся
   (группы убывают: `desc_groups` — best fit и так всё переиспользует). Условие: серия включается, только если
   длина текущей серии больше длины предыдущей.
5. **Режим малой траншеи (новое).** При `T ≤ 100` клеток — «точное попадание, иначе worst fit» вместо best fit.
   На крошечных головоломках KPI дискретен (20/40), и сохранение крупных дыр важнее их дробления.
6. **Ровно столько докопок, сколько нужно**, и укладка в левый край хвостового промежутка (остаток остаётся
   в конце траншеи, где может расти).

## Что проверено и отвергнуто (с цифрами)

- **Блоки арены без ограничения по клеткам** (16 слотов × L): `desc_groups` 0.974 → 0.709. Простаивающая
  резервация заставляет копать в другом месте. Лечится ограничением ёмкости блока (≈64 клетки).
- **Подстройка блока под найденную дыру** (`slots = gl/L`): тест 5 0.748 → 0.679 — классы размазываются
  по мелким дырам и теряют непрерывность.
- **Рост блока по ходу серии** (K[8]=192, «длинная серия получает крупные блоки»): open 29.3007 → 29.3848,
  но оба seed-набора класса `sorted_groups` хуже (0.709/0.749 → 0.700/0.737) — это подгонка под конкретный
  открытый тест 5, а не механизм. Выключено по умолчанию (K[8]=0).
- **Ёмкость блока > 192 клеток**: тест 5 растёт (0.748 → 0.910 при 192), но тест 9 и два seed-набора класса
  падают (sorted_groups 0.693/0.691), поэтому выбрано 96 — лучший компромисс по независимым наборам.

Тест 3 разобран отдельно: выгодное решение — НЕ брать точную дыру 2 м рядом с трубой, которая вот-вот умрёт
(её смерть даёт дыру 5 м под следующую трубу), а взять дыру 4 м. Тест 2 требует обратного — взять большую дыру
маленькой трубой, чтобы получить остаток, точно равный будущей длине. Отличить эти ситуации онлайн нечем:
это чистое знание будущего, поэтому один из двух тестов проигрывается любой парной эвристикой.

## Проверка «подозрительного совпадения» лидеров (сделано по запросу)

Сумма лидеров **30.75747405** воспроизведена независимо как сумма тривиальных верхних оценок
`20·ceil(peak_live/20)` по 15 открытым тестам — совпадение до 8 знаков. Сама оценка корректна (траншея не
укорачивается, длина кратна 20). Дополнительно: два оффлайн-жадины, **знающие будущее** (`scripts/offline_probe.cpp`)
дают только **28.30**, то есть попадание в UB требует не «знания будущего вообще», а полноценной оффлайн-оптимизации
укладки. Вывод: 30.757 online-алгоритмом недостижимо; это оффлайн-оптимум, который решения лидеров, судя по
совпадению на всех тестах, знают заранее. На закрытых тестах такой подход не даёт ничего.
