# Вариант B «portfolio»: портфель политик + выбор по истории (теневые симуляции)

- **Владелец:** Claude (по поручению feni). **Ветка:** `claude/portfolio`. **Файл:** `solutions/portfolio.cpp`.
- Окружение разработки: Windows + MSVC (`scripts/build_*.bat`); решение — один C++17-файл, собирается и g++ (`#ifdef _MSC_VER/_WIN32` для intrinsics и CPU-времени).

## Идея

1. Набор **чистых политик размещения** (best/first/exact-else-worst fit, «арены» для скоротечных труб).
2. Каждая политика на **всей истории команд** прогоняется в своей *теневой* копии траншеи (честный online: тени видят только прошлое).
3. **Реальная траншея** ведётся текущим лидером; лидер выбирается по оценке теней (меньше «непригодного» свободного места) с гистерезисом.
4. Общий **предсказатель времени жизни** трубы (по контексту при укладке) даёт класс T (умрёт скоро) / P (долгоживущая) — нужен политикам-аренам.

## Что выяснилось про тесты (важно для всех веток)

Подробно: `scripts/phase_stats.py`, `scripts/life_stats.py`, `scripts/life_stats2.py`.

- **11 и 15 — две фазы по n/2 команд.** Фаза 1: только трубы 1..7, ~20 % команд — удаления свежих. Фаза 2: только длинные 8..M (M=32 в 11, 40 в 15),
  ~50 % удаления: 82 % — свежие длинные (тяжёлый хвост по возрасту), 18 % — «заметка» по **старым коротким**: указатель идёт от верха стопки
  вниз, удаляя каждую вторую. Длинные трубы не влезают в дыры 1..7 → ~5 % дыр в финале. **Это почти неустранимо:** 15 даёт 0.947 у best fit,
  0.952 у лучших; верхняя оценка 1.0 недостижима (какие короткие умрут — случайно).
- **5 и 9** (серии одинаковых длин по возрастанию, после серии удаляется каждая вторая): смещение удаляемых **фиксировано** (offset 0, step 2 в порядке PID).
  Best fit даёт 0.50 (в дырах длины g не помещаются трубы g+1). Помогает **разделение жертв и выживших по классам** (арены): 5 → 0.85–0.93, 9 → 0.58–0.64.
- **10** — периодический паттерн `3 5 2 5 1 3 1` (сумма 20), массовые удаления по смещениям 0,2,4, затем «1 -K 4»: K — арифметическая прогрессия (+7);
  угадать «кто умрёт следующим» = идеально упаковать (идея «предсказатель следующей жертвы», не сделана).
- **8, 13** — «положи, удали предыдущую» сериями одной длины (5, 6, 7, …), затем волны 5/10/15 с локальной перестановкой удалений; редкие «шумовые»
  трубы живут вечно. **12, 14** — смесь: у каждой длины своя вероятность удаления (14: фаза единиц без удалений, смешанные фазы, длинные в конце).
- **2, 3, 4, 6** — крошечные «головоломки»: нужен exact fit (2: best fit 0.5 → exact-else-worst 1.0); 3: нужно не занимать дыру рядом с трубой, которая скоро умрёт.
- Закрытые тесты (16–30) по весам, скорее всего, продолжают 12–15 (веса 4 и 10), т.е. средние/большие структурные, а не крошечные.

## Устройство `solutions/portfolio.cpp`

- `Alloc` — состояние траншеи: хвост (`tailStart`), дыры в двух хеш-таблицах (по началу и по концу — слияние соседей за O(1)), по размерам 1..39 —
  min-кучи адресов с ленивым удалением, большие дыры (≥ 40) — `std::set`. Дыры имеют **тег** U (обычные) / T (арены скоротечных).
- Политики (`POLS_INIT`): выбор дыры `BEST` / `FIRST` / `EXACTWORST` (точное попадание, иначе наибольшая) / `TFIT` / `SCORED` / `WFN` / `XFIRST`, сторона (`right`), арены (`js`).
  Рабочий набор: `bf-L` (стартовая, самая безопасная), `xw-R` (первые 60 команд — решает крошечные «головоломки», дальше как обычная тень), `ff-L`
  и три политики с аренами (`a99_*`).
- Арена: труба класса T → best fit по T-дырам и (если `tuU`) U-дырам; иначе открывается **чанк** в хвосте размером `clamp(Cdiv × средняя длина T-труб, Cmin, Cmax)`,
  его остаток остаётся T-дырой. P-труба идёт в U-дыры (в малые T-дыры, если `Tsmall > 0`), иначе в хвост. Политика без арен видит T-дыры как обычные
  (иначе утечка пространства при переключении между политиками!).
- `Predictor`: 15 семейств контекстных ключей (длина, позиция в серии одинаковых длин по модулю 2/3, pid mod m, пары/тройки прошлых длин) × 8 горизонтов `8·4^j` команд;
  таблицы «P(смерть за H | ключ)» из завершённых наблюдений («умерла за H» / «дожила до возраста H»); лучшее семейство по горизонту выбирается по префиксной
  кросс-энтропии с затуханием. **Адаптивный горизонт (`js = 99`)**: для класса T берётся горизонт, на котором лучшее семейство сильнее всего выигрывает
  у «общей» вероятности смерти — арены работают и на сериях по 10–20 тысяч труб (масштабируемость; фиксированные горизонты 512/2048 ломались при серии > 1500).
  На больших тестах таблицы обучаются по подвыборке труб (каждая 2-я / 4-я).
- `Engine`: тени + реальная траншея; оценка политики = `live + (1-γ)·свободное + γ·непригодное` (непригодное = дыры короче 25-го перцентиля длин последних 256 укладок), γ=0.5;
  переключение при выигрыше ≥0.5 % (на арены — ≥3 %), не чаще раза в 500 команд (при выигрыше >6 % — не чаще раза в 40). Защита по CPU: если CPU/команду выше 21 мкс
  (после 8192 команд) — «lean-режим» (одна политика, без теней и предсказателя).

## Ловушки, на которых я обжёгся

- Плохой выбор стартовой политики дорого стоит: `xw-R` (exact-else-worst) на 0.4 % лучше best fit на двухфазных тестах, но на очередях (fifo) даёт 0.855 против 0.971.
- Политика без арен обязана видеть T-теги дыр — иначе после переключения «арена → обычная» дыры арен теряются навсегда (было −30 % на некоторых тестах).
- Обновлять траншею/хост стендом: CPU-время процесса в стенде общее для всех тестов — lean-режим там выключен (`leanEnabled() = false`), иначе результаты пакетного прогона искажаются.
- `NEAR` — макрос в `windows.h`; не использовать как имя.

## Что дальше (идеи)

1. **Предсказатель следующей жертвы** (арифметические прогрессии/«удаляется самая свежая») + размещение с учётом соседей, которые скоро умрут (тесты 3, 10).
2. Лучше арены: чанки адаптивного размера, двусторонние, возврат неиспользованного остатка чанка.
3. Выбор политики по «готовности» (usable holes) — сделан в простом виде; можно оценивать по прогонам реальной траншеи на «зеркальном будущем».
4. Подбор весов/порогов автоматически на расширенных наборах (генераторы с вариациями параметров).
